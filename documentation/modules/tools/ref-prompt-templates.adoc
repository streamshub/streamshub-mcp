= Prompt templates

Prompt templates encode Strimzi domain knowledge and guide LLMs through structured diagnostic workflows.

== diagnose-cluster-issue

Structured workflow for diagnosing Kafka cluster issues.

*Parameters:*

* `cluster_name` (required) -- Name of the Kafka cluster
* `namespace` (optional) -- Kubernetes namespace
* `symptom` (optional) -- Observed symptom or issue

*Workflow:*

. Check cluster status and conditions
. Check Strimzi Drain Cleaner readiness
. Check node pool statuses
. Check Strimzi operator and User Operator health
. Check pod health
. Check Kubernetes events
. Read pod logs from unhealthy pods
. Check cluster metrics
. Correlate and summarize

*Usage:* Select this prompt in your AI assistant, provide the cluster name, and the AI will follow the structured diagnostic workflow.

== compare-cluster-configs

Structured workflow for comparing two Kafka cluster configurations.

*Parameters:*

* `cluster_name_1` (required) -- Name of the first cluster
* `cluster_name_2` (required) -- Name of the second cluster
* `namespace_1` (optional) -- Namespace for the first cluster
* `namespace_2` (optional) -- Namespace for the second cluster

*Workflow:*

. Get configuration for cluster 1
. Get configuration for cluster 2
. Compare broker configuration
. Compare resources and JVM options
. Compare listeners and authorization
. Compare component settings (Entity Operator, Cruise Control, Kafka Exporter)
. Compare metrics and logging
. Summarize differences by impact (CRITICAL/HIGH/MEDIUM/LOW)

== audit-security

Security audit of Kafka cluster users, ACLs, authentication, quotas, and certificates.
The server-driven companion is the xref:ref-diagnostic-tools-{context}[`audit_kafka_security` tool], which the prompt now uses as its primary data-gathering step (with the per-tool steps retained as a fallback).

*Parameters:*

* `cluster_name` (required) -- Name of the Kafka cluster to audit
* `namespace` (optional) -- Kubernetes namespace

*Workflow:*

. Check listener authentication configuration and certificate expiry
. Enumerate all users and summarize authentication types
. Audit each user's ACL rules for security concerns (wildcard ACLs, cluster-level access, missing auth/authz)
. Assess overall security posture with high/medium/informational findings
. Provide prioritized remediation recommendations

== troubleshoot-connect

Step-by-step troubleshooting of a KafkaConnect cluster platform issue. For individual connector issues, use `troubleshoot-connector` instead. Also available as the server-driven xref:ref-diagnostic-tools-{context}[`diagnose_kafka_connect`] composite tool.

*Parameters:*

* `connect_cluster` (required) -- Name of the KafkaConnect cluster to troubleshoot
* `namespace` (optional) -- Kubernetes namespace
* `symptom` (optional) -- Observed symptom (for example, "pods crashing", "workers rebalancing")

*Workflow:*

. Check Connect cluster status, replicas, conditions, REST API
. Check connector inventory -- scope detection (all failing vs isolated)
. Check Connect pods for crashes, restarts, resource pressure
. Check Connect logs for WorkerRebalance, OOM, plugin, connectivity errors
. Check Connect worker metrics and resource metrics (JVM, GC, CPU)
. Check Kubernetes events for scheduling and eviction issues
. Correlate and diagnose (deployment/resource/plugin/rebalancing/connectivity)

== troubleshoot-topic

Step-by-step troubleshooting of a KafkaTopic issue. Focuses on topic-specific diagnosis and delegates to `diagnose-cluster-issue` or `analyze-kafka-metrics` for cluster-level problems. Also available as the server-driven xref:ref-diagnostic-tools-{context}[`diagnose_kafka_topic`] composite tool.

*Parameters:*

* `topic_name` (required) -- Name of the KafkaTopic to troubleshoot
* `cluster_name` (optional) -- Kafka cluster name (auto-discovered from topic labels if omitted)
* `namespace` (optional) -- Kubernetes namespace
* `symptom` (optional) -- Observed symptom (for example, "NotReady", "config mismatch", "reconciliation stalled")

*Workflow:*

. Check KafkaTopic status, conditions, and configuration
. Determine scope -- topic-wide or cluster-wide problem
. Quick cluster health gate (redirects to `diagnose-cluster-issue` if cluster is NotReady)
. Check Topic Operator reconciliation logs for this specific topic
. Check Kubernetes events
. Diagnose and recommend (topic config, operator issues, or redirect to cluster prompts)

== analyze-capacity

Capacity analysis of a Kafka cluster.

*Parameters:*

* `cluster_name` (required) -- Name of the Kafka cluster
* `namespace` (optional) -- Kubernetes namespace
* `concern` (optional) -- Specific concern (for example, "storage running low", "planning for traffic increase")

*Workflow:*

. Inventory cluster topology and resource allocation per node pool
. Check pod resource utilization and restart counts
. Assess broker performance metrics (request handler idle, network processor idle)
. Check JVM and resource metrics (heap usage, GC pressure)
. Assess throughput volume and broker balance
. Check replication health and partition distribution
. Assess topic and partition scale
. Check Kafka Exporter consumer lag and partition metrics
. Produce capacity report with utilization, bottlenecks, and scaling recommendations

== troubleshoot-kafka-storage

Step-by-step troubleshooting of Kafka storage issues. Covers full disks, PVC binding failures, volume expansion, and JBOD layout problems. Also available as the server-driven xref:ref-diagnostic-tools-{context}[`diagnose_kafka_storage`] composite tool.

*Parameters:*

* `cluster_name` (required) -- Name of the Kafka cluster
* `namespace` (optional) -- Kubernetes namespace
* `symptom` (optional) -- Observed symptom (for example, "disk full", "PVC Pending", "broker pod CrashLoopBackOff")

*Workflow:*

. Check cluster status
. Inspect PVC status, capacity, and StorageClass expansion capability
. Check storage capacity and disk metrics (capacity, I/O)
. Assess volume expansion options based on StorageClass `allowVolumeExpansion`
. Check node storage pressure via pod health
. Inspect JBOD layout from KafkaNodePool specs
. Check Kubernetes events for storage errors (FailedMount, ProvisioningFailed, VolumeResizeFailed)
. Check broker logs for I/O errors (IOException, No space left on device)
. Produce a structured PVC status table, issue list, and prioritized remediation plan

== troubleshoot-kafka-rebalance

Step-by-step troubleshooting of a stuck or failed KafkaRebalance (Strimzi Cruise Control rebalancing). Also available as the server-driven xref:ref-diagnostic-tools-{context}[`diagnose_kafka_rebalance`] composite tool.

*Parameters:*

* `rebalance_name` (required) -- Name of the KafkaRebalance to troubleshoot
* `namespace` (optional) -- Kubernetes namespace
* `symptom` (optional) -- Observed symptom (for example, "stuck in PendingProposal", "NotReady")

*Workflow:*

. Read the KafkaRebalance state, mode, conditions, optimization result, session ID, auto-approval, and progress ConfigMap name (and the `cluster` field used by later steps)
. Locate the current state in the state machine (`New` -> `PendingProposal` -> `ProposalReady` -> `Rebalancing` -> `Ready`, with `Stopped`/`NotReady`)
. Inspect conditions for goal violations and errors (hard goal violations, invalid broker IDs, excluded-topics conflicts, insufficient metrics)
. Check Cruise Control pod health via `get_kafka_cluster_pods` (the `*-cruise-control-*` pod)
. Check Cruise Control logs via `get_kafka_cluster_logs`
. Check Cruise Control metrics via `get_cruise_control_metrics` (`sampling`, `anomaly`)
. Check Kubernetes events on the KafkaRebalance
. Remediation for common stuck states (approval annotation `strimzi.io/rebalance=approve`, `refresh`/`stop`, `skipHardGoalCheck`)
. Summarize with root cause, severity, state-machine status, evidence, and prioritized remediation

== assess-upgrade-readiness

Pre-upgrade readiness check for a Kafka cluster. Also available as the server-driven xref:ref-diagnostic-tools-{context}[`assess_upgrade_readiness`] composite tool.

*Parameters:*

* `cluster_name` (required) -- Name of the Kafka cluster
* `namespace` (optional) -- Kubernetes namespace
* `target_version` (optional) -- Target Kafka or Strimzi version (for example, "Kafka {KafkaVersion}")

*Workflow:*

. *Pre-flight checks*: Cluster health, operator status, node pools and pods, replication metrics, active rebalance check. Each produces a GO/NO-GO verdict.
. *Safety checks*: Performance and resource metrics (headroom for rolling restart), Drain Cleaner readiness, certificate expiry, Kubernetes events.
. *Verdict*: GO/NO-GO/CONDITIONAL with pre-flight checklist and maintenance window estimate.

Active rebalances (New, PendingProposal, ProposalReady, Rebalancing, Stopped) are a *hard blocker* for upgrades -- a rolling restart during data movement can leave partitions in an inconsistent state.
