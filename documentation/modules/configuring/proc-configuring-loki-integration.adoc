[id='proc-configuring-loki-integration-{context}']
= Configuring Loki integration

Use Grafana Loki for centralized log collection and historical log queries.
When configured, the MCP server uses Loki for centralized log collection instead of querying pod logs directly from Kubernetes.

Benefits:

* Historical log queries beyond pod retention
* Aggregated log search across multiple pods
* Advanced filtering with LogQL
* Better performance for large-scale deployments

== Loki configuration properties

[cols="2,2,3",options="header"]
|===
|Property |Default |Description

|`quarkus.rest-client.loki.url` |`http://localhost:3100` |Loki endpoint URL
|`quarkus.rest-client.loki.connect-timeout` |`5000` |Connection timeout in milliseconds
|`quarkus.rest-client.loki.read-timeout` |`30000` |Read timeout in milliseconds
|`mcp.log.loki.auth-mode` |`none` |Authentication mode: `none`, `basic`, `bearer-token`, or `sa-token`
|`mcp.log.loki.sa-token-path` |`/var/run/secrets/kubernetes.io/serviceaccount/token` |Path to ServiceAccount token
|`mcp.log.loki.tenant-id` |- |Tenant ID for multi-tenant Loki deployments. When set, the server sends this value as the `X-Scope-OrgID` header with every Loki request. Required when Loki runs in multi-tenant mode.
|`mcp.log.loki.unwrap-json` |`false` |Reduce JSON log records (for example OpenShift Logging ViaQ records) to their message field before filtering and before returning them. Set to `true` for OpenShift Logging. See <<loki-log-line-format-{context}>>.
|`mcp.log.loki.json-message-field` |`message` |JSON field that holds the log message when `unwrap-json` is enabled. Accepts a dotted path, for example `log.message`.
|`mcp.log.loki.max-lookback` |`720h` |How far back a query without a time range and without `filter` or `keywords` reaches. Keep it at or below the backend's `max_query_length`. Must be at least `1m`. See <<loki-time-range-{context}>>.
|`mcp.log.loki.filter-lookback` |`1h` |How far back a query with `filter` or `keywords` but without a time range reaches. Capped at `max-lookback`. Must be at least `1m`.
|===

== Setup Loki

Deploy Loki to your cluster using the Loki Operator.
The provided manifests use the Loki Operator from the Red Hat catalog.

[source,bash]
----
# Deploy Loki operator and instance
kubectl apply -k dev/manifests/loki/

# Verify Loki is running
kubectl -n loki get pods
----

== Configure the MCP server

To enable Loki:

[source,bash]
----
QUARKUS_REST_CLIENT_LOKI_URL=http://loki.monitoring:3100
MCP_LOG_PROVIDER=streamshub-loki
----

Alternatively, resolve the Loki service URL dynamically and set it on the running deployment:

[source,bash]
----
# Get Loki service URL
LOKI_URL=$(kubectl -n loki get svc loki -o jsonpath='{.spec.clusterIP}')

# Configure MCP server
kubectl -n streamshub-mcp set env deployment/streamshub-mcp-strimzi \
  QUARKUS_REST_CLIENT_LOKI_URL=http://${LOKI_URL}:3100 \
  MCP_LOG_PROVIDER=streamshub-loki
----

[id='loki-authentication-{context}']
== Authentication

*Basic authentication:*

[source,bash]
----
MCP_LOG_LOKI_AUTH_MODE=basic
QUARKUS_REST_CLIENT_LOKI_USERNAME=your-username
QUARKUS_REST_CLIENT_LOKI_PASSWORD=your-password
----

*ServiceAccount token (Kubernetes):*

[source,bash]
----
MCP_LOG_LOKI_AUTH_MODE=sa-token
# The token is automatically read from the mounted ServiceAccount
----

You can also store credentials in a Secret and reference them on the deployment:

[source,bash]
----
# Create Secret with token
kubectl -n streamshub-mcp create secret generic loki-auth \
  --from-literal=username=your-username \
  --from-literal=password=your-password

# Update Deployment to use Secret
kubectl -n streamshub-mcp set env deployment/streamshub-mcp-strimzi \
  MCP_LOG_LOKI_AUTH_MODE=basic \
  --from=secret/loki-auth
----

== Loki label mapping

Configure how Loki labels map to Kubernetes concepts.
The defaults work with Promtail and Grafana Alloy.

[cols="2,2,3",options="header"]
|===
|Property |Default |Description

|`mcp.log.loki.label.namespace` |`namespace` |Loki label for Kubernetes namespace
|`mcp.log.loki.label.pod` |`pod` |Loki label for pod name
|`mcp.log.loki.label.container` |`container` |Loki label for container name (used to narrow log collection to a single container)
|===

For OpenShift Logging (ClusterLogForwarder):

[source,properties]
----
mcp.log.loki.label.namespace=kubernetes_namespace_name
mcp.log.loki.label.pod=kubernetes_pod_name
mcp.log.loki.label.container=kubernetes_container_name
mcp.log.loki.unwrap-json=true
----

The `unwrap-json` setting makes the log tools filter and return the log message instead of the whole ViaQ JSON record. See <<loki-log-line-format-{context}>>.

Without the container mapping, a `container` filter on the log tools matches no Loki stream and returns no lines.
In that case the response carries a hint in `warnings` that names this property.
The hint appears only when the container's stream has no lines at all within `mcp.log.loki.max-lookback`: when a `filter` or `keywords` search, or a call with `sinceMinutes` or `startTime`/`endTime`, returns nothing, the server first probes the same pod and container over `max-lookback` without the line filters, and adds no hint if the probe finds lines.

[id='loki-log-line-format-{context}']
== Log line format

Some log collectors store each log line in Loki as a JSON record.
OpenShift Logging (ClusterLogForwarder with the default ViaQ data model) stores the log message in the `message` field, next to pod annotations, labels, namespace labels and cluster metadata.

By default, the MCP server returns each Loki line as it is stored, and the `filter` and `keywords` line filters match the whole line.
For JSON records, that includes the record metadata: for example, with OpenShift Logging, `filter: "warnings"` matches every line in a namespace labelled `pod-security.kubernetes.io/warn`, and every line comes back as the whole JSON record, with pod annotations and labels.

Set `mcp.log.loki.unwrap-json=true` to reduce each record to its message inside the LogQL query, before the `filter` and `keywords` line filters run:

* The `filter` and `keywords` parameters match only the log message, not the record metadata.
* The tools return the log message, not the whole JSON record.
* Records with an empty message field (blank log lines) are dropped, because they would otherwise come back as the whole JSON record.
* Plain-text lines, as shipped by Promtail and Grafana Alloy, are returned unchanged.

Enable it for OpenShift Logging, which keeps the original log line, including its log level, in the `message` field.
If your collector stores the message in a different field, set `mcp.log.loki.json-message-field`.

The unwrap is off by default because it applies to every JSON line, not only to records that a collector wraps around the log line.
If your applications log JSON themselves and your collector ships those lines as they are, the unwrap returns only their `message` field.
The `filter: "errors"` shortcut and the `error_count` then no longer see a log level that lives only in another JSON field, for example `{"level":"ERROR","message":"Connection lost"}`.
Leave `mcp.log.loki.unwrap-json=false` in that case, or when you need the other fields of each record.

The unwrap pipeline uses the LogQL `drop` stage, which needs Loki 2.7 or later.
On older Loki versions, leave `mcp.log.loki.unwrap-json=false`.

[id='loki-time-range-{context}']
== Time range

Loki queries always cover a time window.
When a log tool call gives no `sinceMinutes` and no `startTime`/`endTime`, the window depends on the line filters:

* *No `filter` and no `keywords`*: the query reaches back up to `mcp.log.loki.max-lookback` (default 30 days) and returns the newest `tailLines` lines, however old they are.
Loki stops reading once the line limit is filled, so a quiet component, such as the Drain Cleaner that logs only at startup, still returns its lines.
Keep `max-lookback` at or below the backend's `max_query_length` limit (Loki default `721h`), or Loki rejects the query.
Both `max-lookback` and `filter-lookback` must be at least one minute; the server does not start otherwise.
* *With `filter` or `keywords`*: the query covers only `mcp.log.loki.filter-lookback` (default 1 hour).
Loki has no index on line content, so a filtered search reads every line in the window, and a 30-day window would time out on busy clusters.
The response adds a note to `warnings` that says only that window was searched, so an empty result does not read as an all-clear.

With `sinceMinutes` or `startTime`/`endTime`, Loki searches the whole requested window.

[id='loki-tls-configuration-{context}']
== Loki TLS configuration

*Server certificate verification:*

[source,bash]
----
QUARKUS_REST_CLIENT_LOKI_TRUST_STORE=/etc/loki-tls/ca.crt
QUARKUS_REST_CLIENT_LOKI_TRUST_STORE_TYPE=PEM
----

*Mutual TLS with client certificate:*

[source,bash]
----
QUARKUS_REST_CLIENT_LOKI_KEY_STORE=/etc/loki-tls/client.p12
QUARKUS_REST_CLIENT_LOKI_KEY_STORE_PASSWORD=changeit
QUARKUS_REST_CLIENT_LOKI_KEY_STORE_TYPE=PKCS12
----

== RBAC for OpenShift Logging

When using OpenShift Logging with a LokiStack gateway, the MCP server's service account needs the `cluster-logging-application-view` ClusterRole to read application logs.
OpenShift Logging v6.x does not auto-create this ClusterRole (v5.x did), so apply the optional manifests:

[source,bash]
----
kubectl apply -f install/strimzi-mcp/optional/clusterrole-loki-application-view.yaml
kubectl apply -f install/strimzi-mcp/optional/clusterrolebinding-loki-application-view.yaml
----

Without this, Loki queries will return `403 Forbidden`.
The `dev-deploy.sh --ocp --loki` script creates this ClusterRole automatically if it is missing.
