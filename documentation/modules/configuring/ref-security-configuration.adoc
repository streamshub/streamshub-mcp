= Security configuration

== Input sanitization

Every tool argument is passed through the always-on `ArgumentSanitizationGuardrail`, which strips control characters (below U+0020) from all string arguments -- including strings nested in objects and arrays -- while preserving newlines (`\n`), tabs (`\t`), and carriage returns (`\r`). This guards against malformed or malicious input (null bytes, escape sequences) from misbehaving MCP clients. There is no configuration property; the guardrail cannot be disabled.

[id='log-redaction-{context}']
== Log redaction

The server automatically redacts sensitive information from tool responses.
This prevents accidental exposure of credentials, tokens, and other secrets.

The same redaction is applied to the data that diagnostic tools send to the client's LLM through MCP Sampling, so gathered configuration and logs are redacted before they leave the server.
Resource configuration maps that tools return (Kafka, Cruise Control, tiered storage, topic, connector, and bridge `config`) are redacted at the source by key name.

[cols="2,1,3",options="header"]
|===
|Property |Default |Description

|`mcp.guardrail.log-redaction.enabled` |`true` |Enable log redaction
|`mcp.guardrail.log-redaction.custom-patterns[N]` |- |Custom regex patterns for redaction (indexed)
|===

*Built-in redaction patterns:*

* Bearer tokens (`Bearer <token>`) and basic credentials (`Authorization: Basic <credentials>`)
* Passwords in various formats (`password=...`, `pwd:...`)
* API keys (`apikey=...`, `api_key=...`)
* Secrets and tokens (`secret=...`, `secret_key=...`, `token=...`)
* Connection strings with embedded credentials (`scheme://user:pass@host`)
* PEM private key blocks (`-----BEGIN ... PRIVATE KEY-----` ... `-----END ... PRIVATE KEY-----`)
* High-entropy base64 tokens (40+ characters); container image digests such as `sha256:<hex>` are kept

*Built-in redaction by key name:*

A text value is replaced with `[REDACTED]` when the JSON field or configuration key that holds it names a secret, even if the value has no recognizable shape.
For example, `{"database.password": "hunter2"}` and `sasl.jaas.config` values are redacted.
Keys are compared word by word, so `key.converter`, `delegation.token.max.lifetime.ms`, `keystore.location`, and the `secret_name` field that names a Kubernetes Secret are not affected.
Values that are only a configuration-provider reference such as `${secrets:namespace/name:password}` are kept.
In configuration maps, any key containing the word `auth` or `pass` is treated as secret, so `basic.auth.user.info` (Schema Registry credentials in Kafka Connect configs) is redacted.
A bare `Basic <credentials>` value is redacted even when it is not preceded by `Authorization:`.

NOTE: `get_kafka_connector`, `get_kafka_bridge`, `get_kafka_topic`, and `get_kafka_cluster_config` redact secrets in their `config` maps at the source.
This redaction is always on and is not affected by the setting below.

*To disable the response guardrail and the Sampling redaction (not recommended for production):*

[source,bash]
----
MCP_GUARDRAIL_LOG_REDACTION_ENABLED=false
----

*To add custom patterns:*

[source,bash]
----
MCP_GUARDRAIL_LOG_REDACTION_CUSTOM_PATTERNS_0='(?i)ssn\s*[=:]\s*\d{3}-\d{2}-\d{4}'
MCP_GUARDRAIL_LOG_REDACTION_CUSTOM_PATTERNS_1='(?i)x-custom-header:\s*\S+'
----

Or in `application.properties`:

[source,properties]
----
mcp.guardrail.log-redaction.custom-patterns[0]=(?i)ssn\\s*[=:]\\s*\\d{3}-\\d{2}-\\d{4}
mcp.guardrail.log-redaction.custom-patterns[1]=(?i)x-custom-header:\\s*\\S+
----

*Example redaction:*

----
Original: Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
Redacted: Authorization: Bearer [REDACTED]
----

== Response size limits

Prevent excessive response sizes that could impact client performance.

[cols="2,1,3",options="header"]
|===
|Property |Default |Description

|`mcp.guardrail.max-response-bytes` |`500000` |Maximum response size in bytes (500KB)
|===

When a response exceeds this limit, the largest text fields are truncated to fit.

[source,bash]
----
MCP_GUARDRAIL_MAX_RESPONSE_BYTES=1000000  # 1MB
----

[id='rate-limiting-{context}']
== Rate limiting

Control request rates per tool category to prevent resource exhaustion.

[cols="2,1,3",options="header"]
|===
|Property |Default |Description

|`mcp.guardrail.rate-limit.log-rpm` |`0` |Log collection requests per minute (0 = unlimited)
|`mcp.guardrail.rate-limit.metrics-rpm` |`0` |Metrics query requests per minute (0 = unlimited)
|`mcp.guardrail.rate-limit.general-rpm` |`0` |General tool requests per minute (0 = unlimited)
|===

*Recommended production values:* For a typical deployment with a single AI assistant, start with `log-rpm=30`, `metrics-rpm=60`, `general-rpm=120`.
Increase if you have multiple concurrent users or automated pipelines calling the MCP server.

Rate limits are enforced per tool category:

* *Log category* -- `get_kafka_cluster_logs`, `get_strimzi_operator_logs`, `get_kafka_connect_logs`, `get_kafka_bridge_logs`, `get_kafka_mirror_maker_logs`, `get_drain_cleaner_logs`
* *Metrics category* -- `get_kafka_metrics`, `get_kafka_exporter_metrics`, `get_kafka_connect_metrics`, `get_kafka_bridge_metrics`, `get_strimzi_operator_metrics`
* *General category* -- All other tools

To enable rate limiting:

[source,bash]
----
MCP_GUARDRAIL_RATE_LIMIT_LOG_RPM=30
MCP_GUARDRAIL_RATE_LIMIT_METRICS_RPM=60
MCP_GUARDRAIL_RATE_LIMIT_GENERAL_RPM=120
----

When a rate limit is exceeded, the tool returns an error indicating the limit and retry time.
